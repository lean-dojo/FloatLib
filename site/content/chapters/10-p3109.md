The FP8 and FP4 formats of [chapter 09](#/chapter/low-precision-formats-for-machine-learning) assign their NaN, infinity, and zero codes differently. The IEEE P3109 interim report specifies those assignments through four parameters: total width $K$, precision $P$, signedness, and domain. A finite domain has no infinities; an extended domain includes them. Together the parameters determine what every one of the $2^K$ codes means and how an exact real is projected into the format.

The report calls a representable value a *datum*, distinguishing the value from its stored code. It names Binary8p4se, Binary8p3se, Binary4p2sf, and Binary8p1uf for block scales as required instances of the parameterized family. FloatLib models the family and builds arithmetic on its projection rule: compute an exact expression, round to the destination precision, then saturate and encode. We need to check both that the implementation follows this rule and how far rounding can move the value; those are separate proof obligations.

We'll follow version 4.0.3 of the *IEEE Working Group P3109 Interim Report on Arithmetic Formats for Machine Learning* [@p3109InterimReport]. It is a working-group report, not an approved IEEE standard. Section numbers refer to that report: Sections 3.1 and 4.7.2 for decoding, and 4.7.3 through 4.7.6 for projection.

FLoPS, by Tung-Che Chang, Sehyeok Park, Jay P. Lim, and Santosh Nagarakatte,
formalizes P3109 in Lean and studies how saturation and one-bit precision change familiar
numerical algorithms [@flopsPaper]. Its FMCAD artifact also provides executable bit-level
arithmetic with refinement proofs for rounding, saturation, projection, and core operations
[@flopsArtifact]. It is the closest related work to this part of FloatLib. We compare the
[two developments and their proof coverage](#/chapter/external-validation/other-verified-numerical-libraries)
in chapter 16.

## Width, precision, signedness, and domain

A P3109 format is a value of [[FloatLib.Floats.Formats.P3109.Format]] with four parameters: `bitWidth`, the report's $K$; `precision`, its $P$, which includes the implicit leading bit, so only $P - 1$ bits are stored; a `Signedness`; and a `Domain`.

Three proof fields ensure that these parameters define a valid format: $K > 2$, $P > 0$, and $P < K$ for signed formats but $P \le K$ for unsigned ones. Keeping these proofs in the descriptor lets the decoder and projection kernel use the inequalities wherever they are needed. [[FloatLib.Floats.Formats.P3109.Format.signed]] and `unsigned` prove them with `decide` for literal parameters; `ofParameters?` checks them at run time.

From $K$ and $P$ the descriptor derives everything else. The stored trailing bits are $P - 1$, from `trailingBits`. The exponent field, `exponentBits`, has $K - P$ bits in a signed format and $K - P + 1$ in an unsigned one, where the bit that would have held the sign goes to the exponent instead. The bias is a power of two, $B = 2^{w_e - 1}$ for exponent width $w_e$, from `exponentBias`: `exponentBias_signed` gives $B = 2^{K-P-1}$ and `exponentBias_unsigned` gives $B = 2^{K-P}$. This is one more than the IEEE bias $2^{w_e - 1} - 1$ for the same field width, and that unit explains most of the differences from the OCP formats. The smallest normal exponent is $1 - B$, from `minimumNormalExponent`. The report calls the spacing between adjacent values at a given exponent the quantum, one unit in the last place; the smallest quantum in the format is $2^{2 - P - B}$, and `minimumQuantumExponent` names its exponent $2 - P - B$.

The name Binary8p4se follows the report's shorthand from Section 3.2: eight bits, precision four, signed, extended. We'll abbreviate that name to `b8p4se` and keep a few small descriptors at hand so we can read their codes ourselves.

```lean
open FloatLib
open FloatLib.Floats
open FloatLib.Floats.Formats
open FloatLib.Numerics

/-- Eight bits, precision four, signed, with infinities. -/
def b8p4se : P3109.Format := .signed 8 4 .extended

/-- The same layout with a finite datum set: no infinities. -/
def b8p4sf : P3109.Format := .signed 8 4 .finite

/-- Eight unsigned bits with precision eight: one exponent bit and no sign. -/
def b8p8uf : P3109.Format := .unsigned 8 8 .finite

#eval (b8p4se.exponentBits, b8p4se.trailingBits, b8p4se.exponentBias)
-- (4, 3, 8)

#eval (b8p4se.minimumNormalExponent, b8p4se.minimumQuantumExponent)
-- (-7, -10)

#eval (b8p8uf.exponentBits, b8p8uf.trailingBits, b8p8uf.exponentBias)
-- (1, 7, 1)

#eval (P3109.Format.ofParameters? 8 8 .signed .finite).isSome
-- false

#eval (P3109.Format.ofParameters? 8 8 .unsigned .finite).isSome
-- true
```

The signed eight-bit format with precision four has four exponent bits and bias 8, so its normal exponents run from $-7$ to $7$. The unsigned format with $P = K$ is legal and has a single exponent bit; a signed format with $P = K$ would have no exponent field, and the checked constructor refuses it. The `FloatFormat` descriptor of the binary-interchange family requires at least two exponent bits and one fraction bit; P3109 allows one exponent bit and, at $P = 1$, no trailing bits. Its separate descriptor admits these layouts.

## Zero, NaN, and infinity codes

Every P3109 format has exactly one NaN and one zero. It has two infinities, one, or none, depending on signedness and domain. In a signed format the top bit splits the code space at `signBoundary`, $2^{K-1}$: codes below it are positive, codes above it are the same magnitudes negated, and the boundary itself, the code that would be negative zero, is NaN. In an unsigned format NaN is the last code, $2^K - 1$. Both are named `nanBits`.

In an extended domain, positive infinity takes the code just below NaN: $2^{K-1} - 1$, the last code of the positive half, in a signed format, and $2^K - 2$ in an unsigned one. This is `positiveInfinityBits`. A signed extended format puts negative infinity at the top code, `negativeInfinityBits`. Infinities sit at the ends of the finite ranges rather than occupying an entire exponent class, and there is no negative zero anywhere in the family. To see where the finite ranges end, compare the reserved codes in [Figure 10.1](#/chapter/p3109/figure-ch15-code-space) for the three descriptors above and the six-bit, precision-one descriptor used for the tie rule.

![The code space of four P3109 descriptors, each strip running from code 0 at the left to the last code at the right with every class named, and the bit layout of each descriptor to scale on the left](assets/ch15-code-space.png "Four P3109 descriptors and their reserved codes. Signedness and domain determine where zero, NaN, and infinities fit among the finite values.")

For a positive finite code with biased exponent field $e$ and trailing field $t$, with $T = P - 1$ trailing bits, `decodePositiveFinite` computes

$$
x = \begin{cases}
t \cdot 2^{\,2 - P - B} & e = 0, \\[4pt]
(2^{T} + t) \cdot 2^{\,e - B + 1 - P} & e \ge 1,
\end{cases}
$$

The second row is a normal number: the implicit leading one contributes $2^T$, the stored bits fill in $t$, and the exponent scales that $P$-bit integer. The first row is the subnormals of [chapter 02](#/chapter/from-reals-to-machine-numbers), with no implicit one and a fixed scale, so they form a uniform grid down to zero. `decodeNat` wraps this with the reserved-code test, which differs for each of the four combinations of signedness and domain, and [[FloatLib.Floats.Formats.P3109.Format.decode]] restricts the input to a `BitVec` of the descriptor's width; the result is a `NumericalValue Dyadic`: an exact dyadic, a signed infinity, or NaN.

```lean
#eval (b8p4se.nanBits, b8p4se.positiveInfinityBits, b8p4se.negativeInfinityBits)
-- (128, 127, 255)

#eval b8p4se.decode 0x01
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 1, exponent := -10 }

#eval b8p4se.decode 0x08
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 8, exponent := -10 }

#eval b8p4se.decode 0x7e
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 14, exponent := 4 }

#eval b8p4se.decode 0x7f
-- FloatLib.Numerics.NumericalValue.infinity false

#eval b8p4se.decode 0x80
-- FloatLib.Numerics.NumericalValue.exceptional (FloatLib.Numerics.ExceptionalValue.nan none)

#eval b8p4se.decode 0x81
-- FloatLib.Numerics.NumericalValue.finite { negative := true, significand := 1, exponent := -10 }

#eval b8p4se.decode 0xff
-- FloatLib.Numerics.NumericalValue.infinity true
```

Code 1 is the least positive subnormal, $2^{-10}$; code 8 is the least normal, $8 \cdot 2^{-10} = 2^{-7}$; code 126 is the largest finite value $14 \cdot 2^4 = 224$, because code 127 is taken by infinity. In a finite-domain format, code 127 is available for a finite value instead.

```lean
#eval (b8p4sf.nanBits, b8p4sf.maxFiniteBits)
-- (128, 127)

#eval b8p4sf.decode 0x7f
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 15, exponent := 4 }

#eval (b8p4se.maxFinite.toRat, b8p4sf.maxFinite.toRat)
-- (224, 240)
```

`maxFiniteBits` is the largest finite code, and `maxFinite` and `minFinite` are its value and the negation, or zero for an unsigned format. The unsigned format with $P = K$ behaves like fixed point: with one exponent bit and bias 1, codes 0 through 254 form the uniform grid $c / 128$ and code 255 is NaN. The same decoder handles this case.

```lean
#eval (b8p8uf.nanBits, b8p8uf.maxFiniteBits)
-- (255, 254)

#eval b8p8uf.decode 0x7f
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 127, exponent := -7 }

#eval b8p8uf.decode 0x80
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 128, exponent := -7 }

#eval b8p8uf.maxFinite.toRat
-- 127 / 64
```

We can prove these readings for every valid descriptor. The named codes have the meanings specified in the report by `decode_zero`, [[FloatLib.Floats.Formats.P3109.Format.decode_nanBits]], `decode_positiveInfinityBits` under the extended hypothesis, and `decode_negativeInfinityBits` under signed and extended. The ordering theorem [[FloatLib.Floats.Formats.P3109.Format.decodePositiveFinite_strictMono]] says that increasing a positive finite code strictly increases its value, across the subnormal boundary and including $P = 1$. This matters when encoding a value: monotonicity proves that a value within the finite range never lands on a reserved code.

## Projection: round, then saturate, then encode

Conversion follows three steps in the order specified by the report: round the exact input to the descriptor's precision; compare the rounded value with the finite endpoints and apply the saturation rule; encode the resulting datum. The functions `roundToPrecision`, `saturate`, and the encoder behind `projectCode` perform those steps. [[FloatLib.Floats.Formats.P3109.Format.projectValue]] names the result before encoding, so a proof can distinguish the projected datum from its stored code.

A policy is a [[FloatLib.Floats.Formats.P3109.ProjectionPolicy]]: a [[FloatLib.Floats.Formats.P3109.RoundingMode]] and a [[FloatLib.Floats.Formats.P3109.SaturationMode]]. The rounding modes are the nine of Section 4.7.4: toward zero, toward positive, toward negative, nearest with ties away from zero, nearest with ties to even, to odd, and three stochastic modes A, B, and C. Each stochastic mode carries a `RandomBits` value, an exact-width `BitVec` of the $N$ random bits the report calls for, so the operation stays a pure function and an integer too wide for $N$ bits cannot be supplied. The saturation modes are the three of Section 4.7.5: finite, propagate, and none. The report names no default policy, but Section 4.5 requires its minimum operation specializations under the pair (NearestTiesToEven, SatNone) [@p3109InterimReport]. That pair is what our `ProjectionPolicy` defaults to: `nearestEven` is nearest-even rounding with no saturation request, and `finite` adds finite saturation.

The rounding step, [[FloatLib.Floats.Formats.P3109.Format.roundFiniteToPrecision]], first chooses the quantum exponent $Q$, so that the result will be an integer multiple of $2^Q$. For a nonzero input $x$ it is

$$
Q = \max\bigl(\lfloor \log_2 |x| \rfloor,\; 1 - B\bigr) - P + 1,
$$

and one unit in the last place of the result is $2^{Q}$; the `max` includes subnormals in the same formula, and `quantumExponent` names this value for the theorems. The input is then written as $\pm(\ell + r/2^d) \cdot 2^Q$, where $d \ge 0$ is the number of bits of the input that lie below the quantum, $\ell$ is an integer, and $0 \le r < 2^d$; the mode decides between $\ell$ and $\ell + 1$.

Nearest-even uses a different tie rule at $P = 1$. With a single significand bit every nonzero significand is $1$, so Section 4.7.4 tests code parity instead. For a nonzero candidate, the test is whether $Q + B$ is even: at $P = 1$ the code of $2^Q$ is its biased exponent $Q + B$. Zero counts as even. That is `lowerCodeIsEven`; for $P > 1$ it is ordinary significand parity.

```lean
def seventeen : Numerics.Dyadic := { negative := false, significand := 17, exponent := 0 }

#eval b8p4se.quantumExponent seventeen
-- 1

#eval b8p4se.decode (b8p4se.projectCode {} (.finite seventeen))
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 8, exponent := 1 }

#eval b8p4se.decode (b8p4se.projectCode { rounding := .nearestTiesToAway } (.finite seventeen))
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 9, exponent := 1 }

#eval b8p4se.decode (b8p4se.projectCode { rounding := .toOdd } (.finite seventeen))
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 9, exponent := 1 }
```

With four bits of precision the grid around 17 has spacing 2, so 17 is a tie between 16 and 18. Ties to even picks 16 because its significand 8 is even, ties away picks 18, and round-to-odd picks 18 because 9 is odd. The $P = 1$ case needs a smaller format.

```lean
def b6p1sf : P3109.Format := .signed 6 1 .finite

/-- Exactly halfway between the codes 1 and 2 of `b6p1sf`, which denote 2^-15 and 2^-14. -/
def tie : Numerics.Dyadic := { negative := false, significand := 3, exponent := -16 }

#eval (b6p1sf.projectCode {} (.finite tie)).toNat
-- 2

#eval (b6p1sf.projectCode { rounding := .toOdd } (.finite tie)).toNat
-- 1

#eval [0, 1, 2, 3].map fun r =>
  (b6p1sf.projectCode { rounding := .stochasticA (.ofNat 2 r) } (.finite tie)).toNat
-- [1, 1, 2, 2]
```

Here $Q = -15$ and $B = 16$, so $Q + B$ is odd, the lower code 1 is odd, and nearest-even rounds up to code 2; round-to-odd keeps code 1. The stochastic modes turn the discarded fraction $r / 2^d$ into an $N$-bit integer and compare it with the supplied random bits; with the fraction exactly one half and two random bits, half of the four draws round up, as an unbiased rule should at a midpoint. The three modes differ in how they scale the fraction; see `Internal.roundAway` in the [projection kernel](https://github.com/lean-dojo/FloatLib/blob/main/FloatLib/Floats/Formats/P3109/Projection/Runtime.lean).

The carry in this example exposes why significand parity alone would fail. Before rounding, the magnitude is $\tfrac32\cdot2^{-15}$. Rounding its coefficient upward gives $2\cdot2^{-15}$, but a precision-one datum stores that as $1\cdot2^{-14}$: the carry becomes an exponent increment. Both neighbours have normalized significand 1. Their stored exponent codes, 1 and 2, retain the parity distinction that their significands have lost. In the code-space figure, the positive finite codes of `b6p1sf` therefore denote successive powers of two; there is no trailing field between them.

## Saturation and overflow

After rounding, the value is compared with `minFinite` and `maxFinite`. A value inside the interval is unchanged. Outside it, the saturation mode and rounding mode together decide the outcome.

Under `none`, the mode in our default policy and in the report's Section 4.5 specification, a finite value that rounds above the largest finite datum becomes positive infinity in an extended format and NaN in a finite one. As in IEEE 754, rounding toward zero or toward negative returns the largest finite value instead. An infinite input stays infinite where the format has an infinity and becomes NaN where it does not.

Under `finite`, every out-of-range value, finite or infinite, becomes the nearest finite endpoint. Under `propagate`, finite overflow is clamped as under `finite`, but an incoming infinity is kept when the format has one.

```lean
def exact300 : Numerics.Dyadic := { negative := false, significand := 300, exponent := 0 }

#eval (b8p4se.projectCode {} (.finite exact300)).toNat
-- 127

#eval (b8p4se.projectCode { saturation := .finite } (.finite exact300)).toNat
-- 126

#eval (b8p4se.projectCode { rounding := .towardZero } (.finite exact300)).toNat
-- 126

#eval (b8p4sf.projectCode {} (.finite exact300)).toNat
-- 128

#eval (b8p4sf.projectCode { saturation := .finite } (.finite exact300)).toNat
-- 127
```

Three hundred exceeds 224, the largest finite value of `b8p4se`. Under the default policy it becomes code 127, positive infinity; with finite saturation it clamps to code 126; toward zero also returns 126. In `b8p4sf`, which has no infinity, the default policy produces code 128, the NaN, and finite saturation the largest finite code 127.

Rounding comes before the range test, so a value slightly above `maxFinite` can round back down to it. Section 4.7.3 makes this distinction in its first note, and the conversion status follows it. We can see why the order matters by trying adjacent inputs. The values 232 and 233 fall on opposite sides of the overflow threshold:

```lean
def exact232 : Numerics.Dyadic := { negative := false, significand := 232, exponent := 0 }
def exact233 : Numerics.Dyadic := { negative := false, significand := 233, exponent := 0 }

#eval (b8p4se.projectCode {} (.finite exact232)).toNat
-- 126

#eval (b8p4se.projectCode {} (.finite exact233)).toNat
-- 127
```

The grid row containing 224 has spacing 16, so 232 is a tie between 224 and 240. The significand of 224 is 14, which is even, so nearest-even rounds to 224 and nothing overflowed. At 233 the nearest grid point is 240, which is not a datum of `b8p4se`, and saturation turns it into infinity.

Both inputs have leading exponent 7, so substituting in the quantum formula gives $Q=7-4+1=4$. The precision step and the range step then do different work:

| Input | Input in units of $2^4$ | Rounded coefficient | Rounded value | Default projected code |
| --- | --- | --- | --- | --- |
| 232 | $14+\tfrac12$ | 14, even | 224 | `0x7e`, finite |
| 233 | $14+\tfrac9{16}$ | 15 | 240 | `0x7f`, infinity |

Both rounded coefficients fit four bits. The problem with 240 is the encoding: its biased exponent would be 15 and its trailing field 7, giving `0 1111 111`, the code reserved for infinity. The value 224 uses the same exponent with trailing field 6, `0 1111 110`, and is finite. Changing the domain to finite makes the former combination available and 240 representable, without changing the precision rounding at all.

To check that distinction yourself, rerun the two inputs with `b8p4sf` in place of `b8p4se`. Work through precision rounding first, then check whether the rounded value has a finite code.

This is also why the projection proof separates `FitsPrecisionGrid` from the finite range test. A value can fit the precision grid and still have no finite datum in the descriptor. The encoder's in-range hypothesis rules out exactly that collision with a reserved code.

Infinite inputs to a finite-domain format show the three saturation modes side by side.

```lean
#eval (b8p4sf.projectCode {} (.infinity false)).toNat
-- 128

#eval (b8p4sf.projectCode { saturation := .propagate } (.infinity false)).toNat
-- 127

#eval (b8p4sf.projectCode { saturation := .finite } (.infinity false)).toNat
-- 127
```

In a format without infinity, `propagate` clamps exactly as `finite` does; only `none` produces the NaN. Unsigned formats have a lower endpoint of zero, where the same rules apply: a negative input becomes NaN under the default policy and zero under finite saturation or a directed mode that rounds toward it.

```lean
def minusOne : Numerics.Dyadic := { negative := true, significand := 1, exponent := 0 }

#eval (b8p8uf.projectCode {} (.finite minusOne)).toNat
-- 255

#eval (b8p8uf.projectCode { rounding := .towardPositive } (.finite minusOne)).toNat
-- 0

#eval (b8p8uf.projectCode { saturation := .finite } (.finite minusOne)).toNat
-- 0
```

The encoder finishes the projection using the integer arithmetic of Section 4.7.6. It recomputes the exponent row and trailing field from the rounded dyadic, so it does not need to search through the representable codes. The same code path serves a 3-bit descriptor and a 4096-bit one. Its proof obligations are to recover the projected datum and to keep finite results away from reserved codes.

## Constructing and converting P3109 values

Programs use [[FloatLib.Floats.ExecFloat.P3109]], one Lean type per descriptor. It uses the `Codebook` representation from [chapter 12](#/chapter/fixed-point-logarithmic-codebook-and-block-scaled), with the descriptor's `codebook` specifying the meaning of each code. The theorem `decode_eq_format_decode` identifies its decoder with the descriptor's `decode`, so the same decoding theorems apply.

The constructors `zero`, `nan`, `positiveInfinity`, and `negativeInfinity` choose the codes appropriate to the descriptor. The last two take proofs that the requested infinity exists, discharged by `decide` for literal descriptors. `ofFiniteFields?` builds a value from a sign, a biased exponent field, and a trailing field, rejecting reserved combinations. `encode?` accepts a datum only if it is exactly representable; `ofNatBits` reads a serialized word.

```lean
#eval ExecFloat.P3109.toNatBits (ExecFloat.P3109.nan (format := b8p4se))
-- 128

#eval (ExecFloat.P3109.ofFiniteFields? (format := b8p4se) false 15 6).map ExecFloat.P3109.toNatBits
-- some 126

#eval (ExecFloat.P3109.ofFiniteFields? (format := b8p4se) false 15 7).map ExecFloat.P3109.toNatBits
-- none

#eval (ExecFloat.P3109.ofFiniteFields? (format := b8p8uf) true 0 1).map ExecFloat.P3109.toNatBits
-- none

#eval (b8p4se.encode? (.finite exact300)).map BitVec.toNat
-- none

#eval (b8p4se.encode? (.finite { negative := false, significand := 224, exponent := 0 })).map
  BitVec.toNat
-- some 126
```

The field pair $(15, 7)$ is the infinity code of `b8p4se`, so the checked constructor rejects it, as it rejects a negative request for an unsigned format. The checked encoder refuses 300, which is not a datum, and accepts $224 \cdot 2^0$ although the decoder writes it as $14 \cdot 2^4$: representability is decided numerically, by `datumEqual`.

Projection comes in two forms. `project` and `ofDyadic` take an exact dyadic; `projectRat` and `ofRat` take an exact rational and round it once from its numerator and denominator, through `roundFiniteRatToPrecision`. Configured binary floats, posits, integers, and exact finite arithmetic can all supply rational values. The rational path avoids approximating those values as dyadics before the final rounding. The shared conversion API of [chapter 01](#/chapter/using-the-library) uses this path and accepts a `ProjectionPolicy`; its default is nearest-even with no saturation request.

```lean
abbrev B8P4SE := ExecFloat.P3109 b8p4se

#eval (ExecFloat.convert (target := B8P4SE) (3 / 16 : Rat)).value?.map
  ExecFloat.P3109.Conversion.decodeRat
-- some (FloatLib.Numerics.NumericalValue.finite (3 : Rat)/16)

#eval (ExecFloat.convert (target := B8P4SE) (1 / 3 : Rat)).value?.map
  ExecFloat.P3109.Conversion.decodeRat
-- some (FloatLib.Numerics.NumericalValue.finite (11 : Rat)/32)

#eval (ExecFloat.convertWith (target := B8P4SE) (1 / 3 : Rat)
  ({ rounding := .towardZero } : P3109.ProjectionPolicy)).value?.map
    ExecFloat.P3109.Conversion.decodeRat
-- some (FloatLib.Numerics.NumericalValue.finite (5 : Rat)/16)

#eval ExecFloat.P3109.decode (ExecFloat.P3109.ofRat (format := b8p8uf) {} (1 / 3))
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 43, exponent := -7 }
```

Three sixteenths is exact. One third is not: the quantum at that magnitude is $2^{-5}$, so nearest-even gives $11/32$ and toward zero gives $10/32 = 5/16$. In the fixed-point-like unsigned format, one third becomes $43/128$.

The report defines no status flags; these come from FloatLib's conversion API. `inexact` means the returned datum differs from the exact input. `overflow` is `roundedExceedsFiniteRange`: the value rounded to precision in the requested mode lies outside the finite interval, whatever the saturation mode. An input that rounds back to an endpoint therefore does not overflow. `underflow` is `belowMinPositive`: a nonzero input strictly smaller in magnitude than the least positive datum, which is narrower than IEEE tininess. `saturated` is raised only when saturation changed the rounded result and the returned datum is a finite endpoint.

The record has two more fields because it is shared by the conversions in [chapter 01](#/chapter/using-the-library). `wrapped` reports reduction modulo a storage width, which some integer destinations do and no P3109 projection does. `mappedSpecial` is raised when projection changes the class of a special input, for instance when an infinity sent to a finite-domain format becomes NaN or is clamped to an endpoint. A caller can use it to distinguish that case from saturation of a finite input.

```lean
#eval (ExecFloat.convert (target := B8P4SE) (232 : Rat)).status?
-- some { inexact := true,
--   overflow := false,
--   underflow := false,
--   saturated := false,
--   wrapped := false,
--   mappedSpecial := false }

#eval (ExecFloat.convert (target := B8P4SE) (300 : Rat)).status?
-- some { inexact := true,
--   overflow := true,
--   underflow := false,
--   saturated := false,
--   wrapped := false,
--   mappedSpecial := false }

#eval (ExecFloat.convertWith (target := B8P4SE) (300 : Rat) P3109.ProjectionPolicy.finite).status?
-- some { inexact := true,
--   overflow := true,
--   underflow := false,
--   saturated := true,
--   wrapped := false,
--   mappedSpecial := false }

#eval (ExecFloat.convert (target := B8P4SE) (1 / 3000 : Rat)).status?
-- some { inexact := true,
--   overflow := false,
--   underflow := true,
--   saturated := false,
--   wrapped := false,
--   mappedSpecial := false }
```

The value 232 is inexact but does not overflow. Three hundred overflows under both policies; only the finite policy reports saturation, because only it delivered a finite endpoint. One three-thousandth is below $2^{-10}$ and reports underflow.

## Encoding and rounding theorems

If we decode a stored code and encode the resulting datum again, we should get the original code back. `encodeDatumNat_decode` proves this for the direct encoder at every code of every valid descriptor, and `encode?_decode` says the checked encoder accepts every decoded datum and returns its code. In the other direction, `sameDatum_decode_of_encode?_eq_some` proves that a successful checked encoding decodes to the same datum under `SameDatum`. That relation compares finite values numerically, compares infinities by sign, and identifies all NaN payloads because P3109 has one NaN. `datumEqual_eq_true_iff` ties the executable comparison to the relation.

For projection, the value may change, so we ask for a different equality: the stored result must decode to the datum specified by rounding and saturation. Rounding in any of the nine modes lands on the descriptor's grid, `FitsPrecisionGrid`, by [[FloatLib.Floats.Formats.P3109.Format.roundFiniteToPrecision_fitsPrecisionGrid]], including the case where rounding up carries into the next exponent row. The direct encoder maps every in-range grid value back to itself, `decodePositiveFinite_encodePositiveFinite_eq_of_le`. Strict monotonicity supplies the range argument: a value no larger than `maxFinite` never encodes to a reserved code, by `encodePositiveFinite_le_maxFiniteBits`.

The saturation lemmas `sameDatum_decode_encodeFinite` and `sameDatum_decode_encodeSaturate` connect these steps, giving [[FloatLib.Floats.Formats.P3109.Format.sameDatum_decode_projectCode]] and its carrier form [[FloatLib.Floats.ExecFloat.P3109.decode_project]]. The rational path has its own grid-fit lemma, `roundFiniteRatToPrecision_fitsPrecisionGrid`, and reuses the rest, giving `decode_projectRat`. The conversion layer adds [[FloatLib.Floats.ExecFloat.P3109.Conversion.implements_run]], the quantizer contract of [chapter 01](#/chapter/using-the-library), and `sameDatum_decode_run_value`. These results hold uniformly in $K$, $P$, signedness, domain, and policy.

We can now put the concrete descriptors aside. The round-trip example leaves the format as a variable; the two projection examples leave the policy open too. The last checks positive-code monotonicity for the format used above:

```lean
example (format : P3109.Format) (code : BitVec format.bitWidth) :
    format.encode? (format.decode code) = some code :=
  format.encode?_decode code

example (format : P3109.Format) (policy : P3109.ProjectionPolicy)
    (value : NumericalValue Numerics.Dyadic) :
    P3109.Format.SameDatum
      (ExecFloat.P3109.decode (ExecFloat.P3109.project (format := format) policy value))
      (format.projectValue policy value) :=
  ExecFloat.P3109.decode_project policy value

example (format : P3109.Format) (policy : P3109.ProjectionPolicy)
    (value : NumericalValue Rat) :
    P3109.Format.SameDatum
      (ExecFloat.P3109.decode (ExecFloat.P3109.projectRat (format := format) policy value))
      (format.projectRatValue policy value) :=
  ExecFloat.P3109.decode_projectRat policy value

example : StrictMono (fun bits => (b8p4se.decodePositiveFinite bits).toRat) :=
  b8p4se.decodePositiveFinite_strictMono
```

The [direction and error proofs](https://github.com/lean-dojo/FloatLib/blob/main/FloatLib/Floats/Formats/P3109/Projection/Direction.lean) show which grid point the rounding step chooses for the six deterministic modes of the dyadic kernel, before saturation. This is a separate obligation from proving that the encoder preserves the computed datum. The result is always an integer multiple of $2^Q$, by `roundFiniteToPrecision_toRat_eq_int_mul`.

The three directed modes never cross the input, land within one quantum of it, and choose the nearest multiple of the quantum on their side. `roundFiniteToPrecision_towardZero` and `roundFiniteToPrecision_towardZero_maximal` say this for truncation; `roundFiniteToPrecision_towardPositive` and `roundFiniteToPrecision_towardNegative`, with their `_minimal` and `_maximal` companions, say it for the other two.

The two nearest modes stay within half a quantum, by `roundFiniteToPrecision_nearestTiesToAway_abs_sub_le` and [[FloatLib.Floats.Formats.P3109.Format.roundFiniteToPrecision_nearestTiesToEven_abs_sub_le]]. Their tie theorems, `roundFiniteToPrecision_nearestTiesToAway_tie` and `roundFiniteToPrecision_nearestTiesToEven_tie`, pick the larger magnitude or the candidate whose P3109 code is even. The latter includes the $P = 1$ rule; `roundFiniteToPrecision_nearestTiesToEven_tie_even` specializes it to an even significand when $P > 1$. Round-to-odd stays within one quantum, by `roundFiniteToPrecision_toOdd_abs_sub_lt`, and gives an inexact result an odd significand when $P > 1$, by `roundFiniteToPrecision_toOdd_odd`.

The truncation and nearest-even bounds apply to every valid descriptor and dyadic input. The parity theorem requires precision greater than one and an inexact result:

```lean
example (format : P3109.Format) (value : Numerics.Dyadic) :
    |(format.roundFiniteToPrecision .towardZero value).toRat| ≤ |value.toRat| ∧
      |value.toRat| <
        |(format.roundFiniteToPrecision .towardZero value).toRat| +
          (2 : Rat) ^ format.quantumExponent value :=
  format.roundFiniteToPrecision_towardZero value

example (format : P3109.Format) (value : Numerics.Dyadic) :
    |(format.roundFiniteToPrecision .nearestTiesToEven value).toRat - value.toRat| ≤
      (2 : Rat) ^ format.quantumExponent value / 2 :=
  format.roundFiniteToPrecision_nearestTiesToEven_abs_sub_le value

example (format : P3109.Format) (value : Numerics.Dyadic) (hprecision : 1 < format.precision)
    (hinexact : (format.roundFiniteToPrecision .toOdd value).toRat ≠ value.toRat) :
    (format.roundFiniteToPrecision .toOdd value).significand % 2 = 1 :=
  format.roundFiniteToPrecision_toOdd_odd value hprecision hinexact
```

The random bits are inputs, too. [[FloatLib.Floats.Formats.P3109.Format.roundFiniteToPrecision_report_spec]] proves that the shift-based dyadic kernel follows the report's formula for every supplied word. Once that word is fixed, the theorem determines which grid point is returned.

The rational arithmetic path proves that formula for all nine modes, including code parity and exact ties. External precision rounding uses the destination's actual precision and bias; encoding proofs preserve the rounded and saturated datum. The direction and error bounds concern precision rounding before saturation. The conversion theorem [[FloatLib.Floats.ExecFloat.P3109.Conversion.status_overflow_implies_outside]] also proves that a raised overflow flag means the exact input lies outside the destination's finite range.

For small descriptors, such as $3 \le K \le 10$, checking every code is practical. The [independent comparison](#/chapter/external-validation) uses the working group's value tables to check the bit layout. That checks the interpretation of the report, while the theorems above establish the rounding formulas.

## Arithmetic rounds the whole expression

`ExecFloat.P3109.add`, `sub`, `mul`, `div`, and `fma` operate on values of the same format. The corresponding `addTo`, `subTo`, `mulTo`, `divTo`, and `fmaTo` take an explicit destination and policy, with source formats allowed to differ. Finite inputs decode to exact rationals. Addition, subtraction, multiplication, and division form the exact result before calling the destination's rational projection; division requires a nonzero denominator for the finite quotient rule. A fused multiply-add forms $xy+z$ before any rounding or saturation.

That order matters even in eight bits. In `b8p4se`, the largest finite value is 224. All three operands of

$$
16 \cdot 16 - 224 = 32
$$

are representable, and so is the final result. With nearest-even rounding and no saturation request, a separate multiplication produces positive infinity: 256 exceeds the finite range. Subtracting 224 afterwards leaves infinity. With finite saturation, the separate multiplication instead clamps to 224, and the subtraction gives zero. `fmaTo` returns 32 under either policy because it projects only after the subtraction.

The [arithmetic theorem](https://github.com/lean-dojo/FloatLib/blob/main/FloatLib/Floats/Formats/P3109/Arithmetic/Proof.lean) `decode_fmaTo_finite` states exactly this contract for arbitrary finite operands: the decoded output is the same datum as `destination.projectRatValue policy (.finite (x * y + z))`. The general `decode_binaryTo` and `decode_ternaryTo` theorems cover the executable operations and their exceptional cases. Those cases follow the P3109 model: opposite infinities in addition, zero times infinity, and every division by zero produce the single NaN. They do not carry IEEE signaling metadata or status flags.

<a id="square-roots-without-an-approximate-root"></a>

### Square-root rounding by exact comparisons

We can round a square root by comparing squares of rational boundaries. In `b8p4se`, the candidates around $\sqrt{2}$ are $11/8$ and $12/8$. Their midpoint is $23/16$. To decide which is closer to $\sqrt{2}$, compare

$$
2 = \frac{512}{256} < \left(\frac{23}{16}\right)^2 = \frac{529}{256}.
$$

The lower candidate is closer, so nearest-even square root returns $11/8$. The [square-root kernel](https://github.com/lean-dojo/FloatLib/blob/main/FloatLib/Floats/Formats/P3109/Arithmetic/Sqrt/Runtime.lean) uses squared rational boundaries to make these decisions. It implements `sqrtTo`, reciprocal square root `rsqrtTo`, and `hypotTo`; the last forms $x^2+y^2$ exactly before taking its square root. Rounding to precision still precedes saturation.

`roundSqrtRatToPrecision_eq_real` proves agreement with the reference rounder applied to the exact real square root. The configured theorems `decode_sqrtTo`, `decode_rsqrtTo`, and `decode_hypotTo` carry that agreement through encoding. They cover all nine rounding modes, including the stochastic modes with their supplied random word. A negative square-root input and a nonpositive reciprocal-square-root input produce NaN.

For stochastic rounding, `sqrtRoundAway_stochasticA`, `sqrtRoundAway_stochasticB`, and `sqrtRoundAway_stochasticC` connect the squared-threshold tests to the report's floor and nearest-integer formulas. They use the fractional part of the exact real square root and cover every supplied random word. No approximate square root is hidden in that step. Exact rational intermediates can still become large for formats with a wide exponent range.

## Mixed formats and external destinations

Section 4.5 of the report [@p3109InterimReport] names the minimum operation specializations through three sets of formats. FloatLib supplies those specializations, choosing all three of the report's allowed external formats:

| Set | Formats |
| --- | --- |
| `F4` | Binary4p2sf |
| `F8` | Binary8p4se and Binary8p3se |
| `FX` | binary16, binary32, and BFloat16 |

The [mixed-format API](https://github.com/lean-dojo/FloatLib/tree/main/FloatLib/Floats/Formats/P3109/Arithmetic/Mixed) lets each operand have its own type. Exact decoders map finite inputs to rationals, and an explicit `Destination` selects the final projection. This supports conversions and reciprocals among these formats, mixed addition, subtraction, multiplication and division, and fused multiply-add and add-add. The required Section 4.5 specializations use nearest-even with no saturation request. The projection APIs also accept the other report policies.

Fused add-add, `Mixed.faa`, keeps all three terms until the destination is known. For example, take the `b8p4se` inputs 16 and 1 and a binary32 accumulator of $-16$. The exact expression is

$$
(16+1)+(-16)=1.
$$

Rounding the first sum into `b8p4se` would lose the one: 17 is the tie between 16 and 18 examined earlier, and nearest-even chooses 16. The final result would then be zero. `Mixed.faa` sends the exact sum 1 to the binary32 destination. `faa_eq_project_finite` states that contract, just as `fma_eq_project_finite` does for the fused product and addend.

An external destination uses its own precision, bias, and finite endpoints. Binary16 therefore keeps bias 15 rather than adopting a P3109 bias of 16. The [external-destination theorem](https://github.com/lean-dojo/FloatLib/blob/main/FloatLib/Floats/Formats/P3109/Arithmetic/External/Proof.lean) is `project_refines`: encoding the rounded and saturated datum preserves its finite value, infinity sign, or prescribed exceptional representation. There is no second numerical rounding hidden in the encoder.

The exceptional representation follows the report. An external negative zero enters the calculation as the single zero; a result that is zero is written as external positive zero. Input NaN diagnostics collapse to the report's one NaN, and an external NaN result uses the canonical quiet encoding. These adapters are explicit destinations for P3109 operations. Ordinary binary arithmetic continues to use its IEEE signed-zero and NaN rules.

### Scaling before arithmetic

The minimum scaled operations use Binary8p1uf scales with `F4` or `F8` elements and an `F8` or external result. `Mixed.scaledAdd`, `scaledSub`, and `scaledMul` form $sx+ty$, $sx-ty$, and $(sx)(ty)$ exactly, then project once. The result scale is implicitly one. Neither multiplication by an input scale rounds before the main operation.

`scaledAdd_eq_project_finite` and its subtraction and multiplication counterparts state those exact expressions. Exceptional values still obey closed arithmetic: a zero scale multiplied by an infinite element gives NaN, and a NaN scale propagates even if its element is zero. Treating scaling as a bit shift that bypasses those cases would change the operation.

## Comparisons, extrema, and neighboring values

The operation set also includes five comparisons, ten extrema, eight value queries, twelve format queries, and the two neighbor operations. The comparisons are unordered at NaN, including equality with itself. The extrema distinguish ordinary numerical order, magnitude order, and a preference for numbers or finite values when a special operand is present.

For example, `minimumMagnitude (-2) 2` chooses $-2$, while `maximumMagnitude (-2) 2` chooses $2$: equal magnitudes are resolved by numerical order. `minimumNumber` can return a numerical operand when the other is NaN; `minimum` propagates NaN. `minimumFinite` and `maximumFinite` prefer a finite operand even to an infinity. The [extrema proofs](https://github.com/lean-dojo/FloatLib/blob/main/FloatLib/Floats/Formats/P3109/Arithmetic/Extrema/Proof.lean) cover these cases.

Value queries classify zero, one, NaN, infinity, finite values, negative signs, normals, and subnormals. Format queries expose widths, precision, signedness, domain, bias, and the distinguished finite values. The precision-one case makes a query's meaning concrete: there are no nonzero subnormals, so `maxSubnormalOf` returns NaN, as `maxSubnormalOf_eq_nan` proves.

`nextGreaterThan` and `nextLessThan` ask for a strictly greater or lesser datum. In `b8p4se`, the next datum above 224 is positive infinity, and the next above positive infinity is NaN because no greater datum exists. IEEE `nextUp` would instead leave positive infinity unchanged. The neighbor implementation inspects codes directly; the proofs connect consecutive finite codes to numerical order and exclude an intervening representable value.

The listed operations have decoding, projection, ordering, and classification proofs. Those proofs do not establish compliance with every requirement of the interim report.

When we want to check what a particular type means, `#float_info` shows the descriptor, the specification it follows, and the available arithmetic and conversions:

```lean
--

--   storage: exact-width BitVec 8

--   precision (P): 4

```

The output also names the arithmetic and square-root proof contracts. `#float_info!` explains their conditions and the treatment of special values, including the absence of IEEE payload or signaling metadata in the single NaN.

## How P3109 differs from the OCP formats

The formats of [chapter 09](#/chapter/low-precision-formats-for-machine-learning) overlap with P3109 in their FNUZ variants. To compare them, start with the exponent bias. An IEEE-style layout with $w_e$ exponent bits has bias $2^{w_e - 1} - 1$; a P3109 layout with the same field has bias $2^{w_e - 1}$. E4M3FN has bias 7 and a largest finite value of $448 = 1.75 \cdot 2^8$; the signed P3109 format with $K = 8$ and $P = 4$ has bias 8 and a largest finite value of 224 with infinities or 240 without. Every nonzero finite E4M3FN code denotes exactly twice the P3109 value of the same code, and the reserved codes disagree too: E4M3FN puts NaN at `0x7f` and `0xff` and keeps negative zero at `0x80`, while P3109 puts NaN at `0x80` and, in the extended domain, infinities at `0x7f` and `0xff`.

The ONNX FNUZ formats made the other choice. E4M3FNUZ has bias 8, a single zero, no infinity, and its NaN at `0x80`, the negative-zero word. Those are exactly the decisions of a signed finite P3109 descriptor, and we can check the claim over the whole code space.

```lean
open FloatLib.Floats.Formats.BinaryInterchange

/-- Whether a P3109 descriptor and a binary `FloatFormat` give every eight-bit code the same meaning. -/
def sameByteValues (format : P3109.Format) (fmt : FloatFormat) : Bool :=
  (List.range 256).all fun code =>
    let word : Model fmt := Model.ofNatBits code
    match format.decode (BitVec.ofNat format.bitWidth code), Model.toDyadic? word with
    | .finite d, some m => d.toRat == m.toRat
    | .exceptional _, none => Model.isNaN word
    | _, _ => false

#eval sameByteValues b8p4sf FloatFormat.e4m3fnuz
-- true

#eval sameByteValues (.signed 8 3 .finite) FloatFormat.e5m2fnuz
-- true

#eval sameByteValues b8p4se FloatFormat.e4m3fn
-- false

#eval sameByteValues (.signed 8 3 .extended) FloatFormat.e5m2
-- false
```

So [[FloatLib.Floats.Formats.BinaryInterchange.FloatFormat.e4m3fnuz]] and the signed finite descriptor with $K = 8$, $P = 4$ agree on all 256 codes, and [[FloatLib.Floats.Formats.BinaryInterchange.FloatFormat.e5m2fnuz]] agrees with $K = 8$, $P = 3$ the same way. This is an evaluation, not a theorem, and it says that the value sets coincide, not that any two implementations agree on arithmetic. [[FloatLib.Floats.Formats.BinaryInterchange.FloatFormat.e4m3fn]] and [[FloatLib.Floats.Formats.BinaryInterchange.FloatFormat.e5m2]] are not P3109 formats under any descriptor: their bias is one less, E5M2 spends the eight codes of its all-ones exponent on two infinities and six NaNs where P3109 spends three codes on one NaN and two infinities, and both keep a negative zero that P3109 does not have.

```lean
#eval (FloatFormat.e4m3fn.exponentBias, b8p4se.exponentBias)
-- (7, 8)

#eval Model.toDyadic? (Model.ofNatBits (fmt := FloatFormat.e4m3fn) 0x7e)
-- some { negative := false, significand := 14, exponent := 5 }

#eval b8p4se.decode 0x7e
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 14, exponent := 4 }

#eval Model.isInf (Model.ofNatBits (fmt := FloatFormat.e5m2) 0x7c)
-- true

#eval (P3109.Format.signed 8 3 .extended).decode 0x7c
-- FloatLib.Numerics.NumericalValue.finite { negative := false, significand := 4, exponent := 13 }
```

The byte `0x7e` is 448 in E4M3FN and 224 in P3109. The byte `0x7c` is positive infinity in E5M2 and $2^{15}$ in the corresponding P3109 format, whose infinity is three codes higher at `0x7f`.

The code-level agreement with FNUZ covers only part of the P3109 family. `FloatFormat` does not admit unsigned formats with no sign bit, $P = 1$ with no trailing bits, or $P = K$ with one exponent bit. P3109 also classifies its codes differently, with a midpoint NaN, endpoint infinities, and mirrored negative codes. Its separate decoder handles those rules without adding cases to the binary-interchange theorems.

The operation sets differ too. The binary-interchange family provides IEEE arithmetic and status flags, with real-number proofs that assume the IEEE reading of the reserved patterns. P3109 arithmetic evaluates the closed expression and then applies its rounding and saturation policy, including when the destination is a binary format. Matching a value table does not make these APIs interchangeable: their zero, NaN, saturation, and neighbor rules determine what a program observes.

## Using the P3109 APIs

For a conversion proof, [[FloatLib.Floats.Formats.P3109.Format.sameDatum_decode_projectCode]] identifies the datum stored by projection; [[FloatLib.Floats.ExecFloat.P3109.decode_project]] gives the same result for the executable type. Arithmetic reuses this connection after evaluating the exact expression. Use the same-format operations when the operands share a descriptor, the `To` variants when the destination differs, and `Mixed` when the calculation combines P3109 and external binary formats. The destination chooses the final precision and saturation policy.
