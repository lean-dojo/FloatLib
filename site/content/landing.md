lede: FloatLib is a Lean 4 library for executable floating point arithmetic with machine-checked proofs of its numerical behavior.
authors:

In binary32, `0.1 + 0.2` produces a value displayed as `0.3`. Its exact value is `5033165 / 16777216`, or `0.300000011920928955078125` in decimal. FloatLib lets you inspect this value and prove properties of the addition in the same Lean file.

The theorem [`ExecFloat.Proof.add_eq_spec`](#/chapter/using-the-library/how-to-prove-your-first-theorem) states that executable addition returns the same stored value as the format's reference addition. This holds for every certified backend selected by the planner, so proofs about the reference operation also apply to the implementation.

- **Custom formats.** [Define a binary format](#/chapter/using-the-library/which-formats-can-you-use) by choosing its exponent and fraction widths, bias, and encodings for zeros, infinities and NaNs. Shared interfaces also support new representations and rounding rules, with Lean proofs connecting their executable operations to numerical specifications.
- **Rounding theorems.** The [rounding theory](#/chapter/the-mathematics-of-rounding) includes correct rounding, half-ulp error bounds and Sterbenz's lemma for exact subtraction. Each theorem states its hypotheses, such as finite inputs and no overflow. Once these are established, it applies to the corresponding executable operation.
- **Numerical proof automation.** The [`interval` tactic](#/chapter/proving-numerical-bounds) uses bounds on the inputs to prove real inequalities, including inequalities involving elementary functions, by certified evaluation and adaptive subdivision. Its evaluator supports exact rational endpoints, an integer binary grid and custom endpoint formats under a shared containment contract. The [`roundoff` tactic](#/chapter/proving-numerical-bounds/how-to-get-an-error-bound-for-floating-point-code) derives error bounds for configured binary programs and generates the required range conditions.
- **Exceptional values.** The [IEEE model](#/chapter/ieee-binary-formats) specifies NaNs, infinities, signed zeros, comparisons and exception flags. Although positive and negative zero denote the same real number, dividing one by them produces $+\infty$ and $-\infty$, respectively. Theorems about stored words preserve this distinction.
- **Shared interfaces for numerical formats.** IEEE binary and decimal, [small ML formats](#/chapter/low-precision-formats-for-machine-learning), [posits](#/chapter/posits-and-the-quire) and [P3109](#/chapter/low-precision-formats-for-machine-learning/what-is-ieee-p3109) use the same numerical interfaces as fixed point, logarithmic, codebook and block-scaled representations. Posits also provide exact quire accumulation within its capacity, and correctly rounded roots, powers, exponentials and logarithms.

For each operation, the planner selects an implementation from the [backend kernels](#/chapter/performance): lookup tables, machine-word algorithms or limb arithmetic for wider values. Every certified implementation has a proof that it agrees with the specification. Lean erases proof terms during compilation, so these proofs add no runtime checking [@leanReference]. In the public-call benchmarks, binary64 addition, subtraction and multiplication are faster than MPFR at the same precision. The [performance chapter](#/chapter/performance) reports measurements from 2 to 4,096 bits, including the cases where MPFR is faster.

The proofs establish agreement with FloatLib's specifications. Independent tests also compare those specifications and implementations with external libraries. Against SoftFloat and MPFR, all 154 billion binary16 and bfloat16 operation pairs and binary32 square roots agreed in value and all five flags, in each of the four rounding directions IEEE 754 requires for binary formats. FloatLib also matched Berkeley TestFloat on more than 102 million cases in wider IEEE formats. The binary elementary functions matched MPFR on every case in the test corpus. Comparisons with MPFX found four bugs, which we reported upstream. Differences from SoftPosit are [explained in the posits chapter](#/chapter/posits-and-the-quire/how-we-compare-posits-with-universal-and-softposit). The [external validation chapter](#/chapter/external-validation) describes the inputs, results and scope of each comparison.
